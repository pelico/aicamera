# 《拍照构图与姿势引导 App 开发任务书》评审

评审人：实现侧 ｜ 日期：2026-10-09 ｜ 对象：`docs/开发任务书`（并对 `pelico/aicamera` 现状做了核对）

---

## 0. 总体结论

这是一份**质量明显高于常见水平**的任务书。三点做得特别对：

1. **把「不能验证的别假装闭环」写成了设计原则**（第 1 节原则 2）。「手机降到腰部」只能做固定文案、
   机位高度不可测量 —— 这一条如果没写，后面一定会有人做假的实时反馈。
2. **区分了低频量与高频量**（场景 1~1.5 s + 滞回，姿态高频 + 平滑）。这直接命中了上一版失败的核心。
3. **标注了「建议起点」和「待核实」**，并且明确禁止引用无来源数字。这在 AI 协作里非常难得。

诊断也准：当前 App 最致命的问题是**完全不知道人在哪**——同一个场景下，
无论人站在画面什么地方、什么景别，给出的建议都一样。L1/L4 是补这个洞的正确方向。

**但有一处需要处理的关系，任务书没有明说：**

> 上一版转向时定过一个原则：「明确不做姿态估计，只判断景」。
> 本任务书的 L1/L4 等于把姿态检测请回来了。

这不矛盾，但必须说清为什么：**v1 的不稳定来自"小 CNN 回归出一个构图框"，
而 MediaPipe Pose 是经过大量验证的检测器**，两者可靠性不是一个量级。
代价是体积、低端机性能、以及它自己的失效模式（侧身、遮挡、宽松衣物、多人）。
这个决策要显式记录，否则半年后会有人翻旧账。

## 1. 替你核实掉的「待核实」项

任务书里标了若干待核实，我逐条查了官方文档与仓库元信息。**结论只在这份文档范围内有效，
商用前请按各自的 LICENSE 正文再核一遍。**

| 条目 | 核实结果 | 来源 |
|---|---|---|
| Places365 许可证 | GitHub SPDX = **MIT**（不是 CC BY） | GitHub API `CSAILVision/places365`，2026-10-09 查 |
| MediaPipe minSdk | 官方 Setup 文档要求 **Android SDK 24+**，与现项目 minSdk 24 一致 | developers.google.com/edge/mediapipe/solutions/setup_android |
| MobileCLIP 仓库 | 链接已失效（301），现名 **`apple-aiml-research/ml-mobileclip`**，LICENSE 正文是 **MIT**（GitHub 因含 © 符号识别成 NOASSERTION） | GitHub API 重定向 + license 正文 |
| ai-edge-torch | 链接已失效（301），现名 **`google-ai-edge/litert-torch`**，**Apache-2.0** | 同上 |
| Chinese-CLIP | **MIT** | GitHub API `OFA-Sys/Chinese-CLIP` |
| open_clip | 仓库 LICENSE 正文为 MIT 风格，但 SPDX = **NOASSERTION**；且其发布的**模型权重另有条款**，不可默认可用 | 同上 |
| rembg / onnx2tf | 均 **MIT** | 同上 |

另外补充一个任务书没有但必须知道的坑：

> **MediaPipe 的 `.task` 模型文件从 assets 加载时必须声明不压缩**，
> 否则运行时找不到/打不开模型。要在 `build.gradle.kts` 里加 `task`。
> 当前工程只声明了 `onnx` 和 `tflite`（`app/build.gradle.kts:28`），接入时需补上。

## 2. 任务书与现有代码的差距（动手前必须知道）

任务书第 0 节说"以仓库实际代码为准"，我核对了，有几处对不上：

### 2.1 数据契约不存在，需要新建适配层

第 4 节定义的 `SceneResult` / `PersonResult` / `Guidance` **当前代码里没有**。现有的是：

| 任务书 | 现有代码 | 差距 |
|---|---|---|
| `SceneResult`（coarse + top-3 fine + attrs） | `ScenePrediction(label, prob, zh, group)` | 无层级、无 attrs 结构 |
| `PersonResult`（bbox / 33 landmarks / shotSize / facing） | **不存在**，全 App 无人检测 | 需从零建 L1 |
| `Guidance`（text / severity / priority / source / target） | 不存在，当前是"整个姿势卡片一起显示" | 需新建仲裁层 |

建议：**不要直接改现有数据类，先加一层 `contract/` 包定义新契约，内部做适配**。
这样三个层的实现可以并行，互不阻塞。

### 2.2 现有 45 条模板**不能直接驱动 L4 角度匹配**

`FigurePose` 现在是给 Canvas 画图用的参数：

```kotlin
data class FigurePose(
    val facing: BodyFacing,
    val armNearDeg: Float = 18f,   // 手臂向外抬起，画图用
    val armFarDeg: Float = -12f,
    val legSpread: Float = 0.18f,
    val lean: Float = 0f,          // -1..1
    val headTurn: Float = 0f
)
```

这些是**手调的绘制参数**，不是可测量的关节角度，也没有 `weights` / `tol_max_deg`
（`grep -c "tol|weight|elbow|knee"` 结果为 **0**）。

含义：**任务书附录 A 的 JSON schema 是对的，但现有 45 条模板要进闭环，必须逐条重新产出角度数据**，
不是改个数据格式就行。这也解释了为什么 M2 只做"首批 10 条"是合理的 —— 建议真的只做 10 条。

好消息：`Placement(cx, footY, height)` 与附录 A 的 `target_center` + `bbox_h_ratio`
语义基本对齐，5.2 的落点目标可以直接复用，不需要重做。

### 2.3 DeviceTier 目前是**死代码**

任务书说"保留 DeviceTier 分档，把姿态层帧率纳入分档"。实际情况：
`DeviceTier` 出了定义文件外，**唯一调用是在 BenchmarkResult 里拼一句展示文案**，
场景间隔是 `CameraScreen.kt:57` 的硬编码常量 `SCENE_INTERVAL_MS = 1500L`。

所以这项不是"保留"，而是"**重新接上**"。

### 2.4 两处配置符合任务书要求，无需返工

`KEEP_ONLY_LATEST` + `320×240` 抽帧（`CameraScreen.kt:103-105`）已符合要求 ✅
但要注意：**这个分辨率对 MediaPipe 姿态检测偏低**。姿态层可能需要更高的分析分辨率，
或者挂两个 ImageAnalysis use case（CameraX 允许），这点任务书没提，建议补。

## 3. 我建议调整的地方

按优先级排：

### P0 —— 先做这个，优先级高于所有功能开发

**`pelico/BuNanYou` 公开仓库里提交了签名文件 `keystore/aicompose-release.jks`（2750 bytes），
且任务书说密码写在 README 里。**

核实结果：**属实**。这意味着任何人都可以用一个和你同名的签名去发布包。
处置顺序：

1. 从 Git 历史中彻底清除（BFG / `git filter-repo`），不是删文件就行 —— 删了仍在历史里
2. 生成全新 keystore，用 Keystore / Google Play App Signing 托管
3. README 里的密码视为已泄露，连同已构建过的 release 包一起作废

这件事不影响离线 Demo，但只要这个 App 有朝一日对外分发，它比任何功能都重要。

### P1 —— 评测集规模下调：300~500 张 → 起步 100~150 张

任务书建议 300~500 张。以一个人 + 一台手机的实际工作量，这个规模会让 M0 直接卡住一个月，
而 M0 的目的是**拿到基线和验收脚本**，不是拿完美数据。

建议：**10 个场景 × 每场景 10~15 张 = 100~150 张**，先跑通流程和脚本，再按需扩。
同时把「60 秒稳定性」这类需要视频的指标拆出来单独测 —— 它和静态图片评测不是一回事，
用 10 段 60 秒录像比 500 张照片便宜得多。

### P2 —— M3（CLIP 零样本替换 Places365）应降级为「有条件执行」

这是全篇**风险最高、确定性最低**的一项，理由：

- 结论性地讲：场景标签的用途是**选模板**。粗类判准就够了 ——
  古镇判成 courtyard、花田判成 field/cultivated，通常**不改变推荐的姿势**。
  真正影响体验的是"有没有这个粗类"，而 Places365 的 365 类覆盖是够的。
- 换成 CLIP 要付出：图像编码器端侧速度（手机实拍未知）、导出工具链风险、
  以及丢掉已经写好的 `SceneLabels.kt`（365 类中文名 + 本土映射）。这三件都不便宜。
- **而且这些收益目前全是假设** —— 任务书自己也写了"M3 评测前不得对外宣称"。

建议改成：**先用 M0 的评测集测 Places365 基线的粗类 top-1。只有当基线明显不达标时，
再并行启动 CLIP 试验，且以「同接口、可开关」的方式接入，不要先拆后建。**

### P3 —— 参考图/剪影：MVP 不要依赖 rembg 抠图和真人参考照

任务书 5.7 的生产管线要求：自拍或授权拍摄 → MediaPipe 提取关键点 → rembg 抠图 → PNG + JPG。
其中**参考图是唯一的版权与肖像风险点，也是最费人力的一环**。

但闭环需要的是**关节角度**，不是真人照片。更省的做法：

> 模板 JSON 里存 33 点 landmarks → 叠加层直接用这组点渲染骨架/轮廓 →摆放者照着骨架对齐。

这样 MVP 完全不需要真人素材，也没有版权问题，APK 也不涨。
**真人参考图放到 M4 之后作为"好看但非必需"的增强**。

### P4 —— 模板总量：60~100 条 → 先 10 条，且明确「不支持多人」

60~100 条的工作量主要不在写，在**逐条验证"真人能不能摆出来"**。
而 10 条能跑通闭环 + 10 条质量过硬，价值远大于 100 条没验过的。

多人入镜：任务书说"默认只跟踪占比最大的一人"。建议在 UI 上显式说明
（检测到多人时提示"当前仅引导画面中最主要的一人"），不要静默选一个人然后给出可能错的引导。

### P5 —— 坐标系统一，这是接 MediaPipe 最容易出隐蔽 bug 的地方

任务书提到了镜像和旋转，但没提到这两条实际会花掉最多时间的：

1. **旋转只能处理一次。** 现有 `FrameConverter` 已经按 `rotationDegrees` 把 YUV 转成了正立的 Bitmap。
   MediaPipe 又要求传入 `rotationDegrees`。**如果都传，会转两次**。
   必须在一条路径上约定死：所有下游拿到的就是正立帧，MediaPipe 传 0。
2. **分析坐标系 ≠ 预览坐标系。** ImageAnalysis 是 320×240，PreviewView 是全屏且按 FIT/CROP 缩放。
   叠加层如果直接用分析帧坐标画，在高瘦屏幕上会整体错位。
   必须做一次 `分析分辨率 → 预览可视矩形` 的映射，并单独写测试（这也是 v1 可能存在的隐患）。

## 4. 建议的执行顺序（针对单人 + AI 协作的实际节奏）

```
第 0 步  [半天]  吊销 BuNanYou 的 keystore，从历史清除，换新        ← 用户操作
  ↓
M0-lite  [2~3天] 评测脚本（离线跑 Places365 出粗类 top-1）+ 100~150 张评测集骨架
                 + 真机测量页补 MediaPipe 的延迟项
  ↓                                    ↓
M1       [1周]   接 MediaPipe Pose lite → PersonResult          ← 并行：M3 候选模型离线对比
                 景别判定 / 三分落点 / 水平仪 / 指令仲裁 + 横幅             （只做离线，不进 APK）
                 **不引入任何新场景模型**
  ↓
M2       [1周]   10 条模板 JSON + 角度特征 + 状态机 + 变绿/震动
  ↓
M3       [条件]  仅当 M0 基线不达标时才做
  ↓
M4/M5    后置
```

M1 是性价比最高的一段：**不碰最有风险的模型替换，但用户感知提升最大** ——
让用户「能看懂一条、一次只给一条」的指令，比「场景标签再准 5 个点」重要得多。

## 5. 补进「已踩过的坑」清单

在任务书第 2 节的基础上追加：

| 坑 | 现象 | 处理 |
|---|---|---|
| MediaPipe `.task` 资源被压缩 | 运行时加载模型失败 | `noCompress += "task"` |
| 帧旋转两次 | 竖屏时姿态全反 | 约定正立帧只转一次，MediaPipe 传 0 |
| 分析帧坐标直接画叠加层 | 高瘦屏上引导整体偏移 | 分析→预览矩形映射 + 单测 |
| VIDEO/LIVE_STREAM 模式时间戳单位 | 传 ns 会导致时间戳单调性报错 | 传 ms（`SystemClock.elapsedRealtime()`） |
| `latest.release` 依赖 | 自动升级引入不兼容 | 锁定具体版本号（如 `0.10.14`） |
| MediaPipe native 库多 ABI | APK 暴涨 | 保持现有 abiFilters（arm64-v8a + armeabi-v7a） |
| quantization 想当然 | ORT 上 int8 因 depthwise 慢 12 倍 | 量化前后必须实测（任务书已提及，此处保留） |

## 6. 一句话总结

方向正确、诊断准确、工程纪律好 —— **唯一的问题是它按 6 个 agent 并行来规划的，
而实际大概率是"你 + 我"串行推进**。所以真正要做的取舍是：

> **先把 M0(小) + M1 做完并装上真机**，拿到第一段"这东西真的能用了"的体感，
> 再决定要不要投入 M3 的模型替换和 M4 的内容海。

在此之前，先去把那个泄露的 keystore 处理掉。
