# 评测方案

评测的目的只有一个：**给「要不要做某件事」提供判据**。不是为了得出一个好看的分数。

目前唯一自动化的是场景粗类评测（`tools/eval_scene.py`）。姿态层的评测还没做自动化，
原因写在最后 —— 那需要先把 `pose_specs.json` 校准好，否则测的是错的 using``东西。

---

## 1. 场景评测（已可跑）

### 目录结构

```
evalset/
├── WATER/        # 子目录名 = 认为正确的粗类，大写
│   ├── img_001.jpg
│   └── ...
├── NATURE/
├── FIELD/
├── URBAN/
├── ARCH/
├── INTERIOR/
├── TRANSPORT/
└── GENERIC/
```

粗类取值就是 `contract/Perception.kt` 里 `SceneCoarse` 的枚举名。

### 跑

```bash
# 先只验证目录结构，不需要任何深度学习依赖
python tools/eval_scene.py --root evalset --dry-run

# 正式跑
python tools/eval_scene.py --root evalset --json eval_report.json

# 每类抽 10 张先试流程
python tools/eval_scene.py --root evalset --limit 10
```

依赖：`numpy` `Pillow` 以及一个 TFLite 运行时（`ai-edge-litert` / `tflite-runtime` / 完整 `tensorflow` 三者任一）。

### 脚本的两个设计决定

1. **分组规则从 Kotlin 源码解析，不在 Python 里重写。**
   `SceneLabels.groupOf` 的 12 条 `has(...) -> SceneGroup.X` 规则和 `SceneResult.from` 的
   粗类映射是在脚本启动时读出来的。重写一遍的结果是两边迟早漂移，
   App 改了分组而评测还在用旧规则，测出来的数字就是假的。

2. **预处理与 App 逐行对齐。**
   中心裁剪 → 双线性缩放到 224 → /255 → ImageNet 归一化 → NCHW。
   `SceneClassifier.kt` 里是多少，这里就是多少，包括 softmax。

### 规模：先 100~150 张，不要一上来 300~500

M0 的目的是**拿到基线和跑通脚本**，不是拿到完美数据。建议：

| 粗类 | 建议张数 | 说明 |
|---|---|---|
| WATER / NATURE / FIELD | 各 15~20 | 这三个是模板覆盖最密的 |
| URBAN / ARCH | 各 15~20 | 国内古镇、古城这类要单独放，看会不会被判成 courtyard |
| INTERIOR / TRANSPORT | 各 10 | 覆盖度低，有就行 |
| GENERIC | 可有可无 | 兜底类，判错了影响也不大 |

采集要求：**必须是真实手机取景的照片**，不要用网图。
原因是 Places365 的输入分布和「站在那儿举着手机拍」不完全一致，
用网图测出来的基线会骗人。

### 判据

跑完看最后三行输出：

- **≥ 80%**：粗类基线达标。M3（把 Places365 换成 CLIP 零样本）**可以先不做**，
  把力气花在校准 `pose_specs.json` 上收益更大。
- **65% ~ 80%**：灰区。看混淆矩阵集中在哪两类：
  - 如果是 URBAN ↔ ARCH 这种本来就容易混的，且**换成 CLIP 也不一定改得准**，就先忍着；
  - 如果是某个类被大量判成 GENERIC，说明缺的是标签覆盖而不是模型，补 `SceneLabels` 的分组规则更划算。
- **< 65%**：先别急着换模型，排查三件事：
  图片是不是真实取景、预处理有没有对齐、某些类的中文分组是不是写漏了。

## 2. 姿态层评测（暂未自动化，有意为之）

姿态闭环的正确性取决于 `pose_specs.json` 里的角度目标。
这些目标现在是**几何推断的初值**（全部 `verified: false`），在没有真人采样之前，
跑任何「姿势匹配准确率」的评测，测的都是这份没校准的数据 —— 数字本身不可信。

顺序应该是：

```
校准（App 内置复制角度按钮）→ 每条 5~10 次采样 → 更新 JSON 并把 verified 翻 true
                                                    ↓
                                        才有资格跑闭环评测
```

校准流程：

1. 取景页选一个有 spec 的模板（姿势库里标「可校准」的）
2. 按步骤把姿势摆到位
3. 到「性能实测」页点「复制当前角度」→ 拿到一组 `angles`
4. 同一个姿势重复 5 次以上，取中位数写进 `pose_specs.json`
5. `verified` 改为 `true`

校准完再做的两项评测：

- **静态闭环准确率**：同一个人对同一模板摆 10 次，看 `Guidance` 多久变成「可以拍了」
- **60 秒稳定性**：录像法测，和静态图不是一回事，要单独做 10 段 60 秒视频，
  看的是「有没有抖动 / 跳变 / 中途丢人」，而不是准确率

## 3. 现在还不测，但要知道存在的项目

| 项目 | 为什么不测 |
|---|---|
| 建议的「美学水平」 | 没有可靠的主观评分对照，NIMA 只能给参考值 |
| 机位高度 | 测不出来，产品上已明确做成固定文案 |
| 正脸 / 背面 | 2D 骨架投影上两者同构，`PersonResult.facing` 里刻意不出现 BACK |
| 多人 | 当前设计只引导占比最大的一人，UI 已显式说明，不假装支持 |
